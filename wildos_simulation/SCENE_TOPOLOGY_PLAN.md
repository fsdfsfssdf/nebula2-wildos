# 场景拓扑改造方案（v2 草案，待评审）

> 目标：把"一条直路"变成"可采样、可复现、每个场景针对一条指标"的航道网络。
> 本文只描述设计与拆分，评审通过后再动 `generate_terrain_worlds.py`。

## 1. 为什么不走"做一张更大的地图"

官方视频里的场景是真实世界，不可复刻；我们需要的也不是"像"，而是"能区分方法好坏"。

- 统计量来自**布局分布**，不来自单张地图的精细度；
- 单张大图不可复现，做不了 A/B，调参会过拟合到那一个场景；
- 一张图跑一次 10–15 分钟，二十个 seed 才有统计意义。

结论：**20 个随机小场景 > 1 个精美大场景**。复杂度用结构堆，不用美术堆。

## 2. 现状盘点

`scripts/generate_terrain_worlds.py` 目前能产出：

- 三角网格路面 + 余弦平滑高程（三档平均坡度 4.19% / 5.50% / 7.85%）
- 路肩、散石、巨石、篱笆、一棵树、地标（红色目标房子）
- 一条线性走廊，约 30–40 m，宽度固定，无分叉

缺的是：拓扑（岔路/环路/死胡同）、遮挡、植被密度、"看着能走其实不能走"的地面、
窄门、以及场景真值标注。

## 3. 设计原则

1. **场景是数据不是代码**：YAML 描述 → 生成器渲染，新增场景不改 Python。
2. **每个场景自带真值**：输出 `scenario.json`（目标坐标、起点位姿、分支、期望路径），
   指标脚本直接读它，不用手抄坐标。
3. **随机可复现**：一切随机数从 `seed` 派生，同 seed 同场景。
4. **难度靠结构**：岔路、遮挡、死胡同、不可通行斑块，而不是贴图精度。
5. **一次只加一种原语**：加完先单场景 smoke，通过后再进批量。

## 4. 场景 DSL 草案

```yaml
name: fork_deadend_01
seed: 7
spawn: {x: 0.0, y: 0.0, yaw: 0.0}

surface:
  terrain_level: 2        # 复用现有三档坡度
  width_m: 3.0
  shoulder_m: 1.0

topology:
  - id: A
    type: line
    from: [0, 0]
    to: [18, 2]
  - id: B
    type: fork
    at: A.end
    branches:
      - {id: B_left,  heading_deg:  35, length_m: 22}
      - {id: B_right, heading_deg: -20, length_m: 14}
  - id: C
    type: blocker          # 在左支末端放一辆"停着的车"
    at: B_left.end
    footprint_m: [2.0, 4.5]

occluders:
  - {type: building,     at: [26, 10], size_m: [8, 8, 6]}
  - {type: tree_cluster, at: [20, -6], radius_m: 3, count: 5}

vegetation:
  density: 0.4             # 0 = 光秃，1 = 密林
  keep_clear_m: 1.2        # 路面必须留空的半径

target:
  type: red_house
  at: [30, 12]
  hidden_from_spawn: true  # 生成时做射线校验，起点必须看不见

evaluation:
  record_goal: true
```

## 5. 拓扑原语与它检验的东西

| 原语 | 检验什么 | 现状 |
| --- | --- | --- |
| `line` | 连通性、基础回归 | 已有 |
| `fork` | 前沿打分到底在不在选方向 | 新增 |
| `loop` | 图记忆能否闭合并避免重复探索 | 新增 |
| `dead_end` | 回退能力（论文 Table 2 的核心） | 新增 |
| `blocker` | 死胡同成因：停着的车、石堆、塌方 | 新增 |
| `gate` | 窄通道：最小离障距离、Nav2 宽度余量 | 新增 |
| `occluder` | 目标定位误差、末段接近是否合理 | 新增 |
| `patch`（不可通行地面） | 可通行性是否真的起作用：看着像路但走不了 | 新增 |

`patch` 是最关键的一个。当前地形几乎全可走，视觉可通行性和几何前沿会给出几乎一样的结果，
仿真永远区分不出 WildOS 的价值。要在视觉上"像路"、在物理上"走不了"（泥沼、深沟、密灌木）。

## 6. 生成流程

1. **解析**：YAML → 拓扑图（节点、边、属性）。
2. **布局**：边 → 中心线折线（限制最小转弯半径）；按 `width_m` 生成左右边界点。
3. **路面网格**：沿用现有三角网格 + 余弦高程；分叉处用圆盘叠加或扇形拼接补齐。
4. **资产放置**：遮挡物、植被、巨石按 `keep_clear_m` 采样（网格抖动或泊松盘），
   保证路面不被堵死。
5. **标注**：输出 `scenario.json`（真值）+ 世界 SDF + 一张俯视预览图。

## 7. 难度分级与验收

| 级别 | 结构 | 用途 |
| --- | --- | --- |
| L1 | 直路（现有 terrain_01） | 回归，确认没改坏 |
| L2 | 直路 + 一个岔 + 一个遮挡 | 方向选择、末段接近 |
| L3 | 岔 + 死胡同 + 封路 | 记忆与回退 |
| L4 | L3 + 窄门 + 不可通行斑块 + 植被 0.7 | 压力测试 |

每级验收：headless 能跑完、五类指标齐全、无卡死、`scenario.json` 与地图一致。

## 8. 与指标的对应

| 指标 | 数据来源 | 需要场景提供什么 |
| --- | --- | --- |
| 成功率 | 多 seed 汇总 | 明确的成功判据（到达 + 看见） |
| 绕路比 | `trajectory.csv` | 起点与目标真值 |
| 目标定位误差 | 三角化输出 vs `scenario.json` | 目标真实坐标 |
| 红像素占比 | 终点前相机图 | 目标必须一开始被遮挡 |
| 稳定性 | `trajectory.csv` 的 attitude / clearance / stall | 起伏地形、窄门、障碍 |

## 9. 工作量拆分

| 阶段 | 内容 | 预估 |
| --- | --- | --- |
| P0 | 轨迹记录 + 指标汇总 | 已完成 |
| P1 | DSL 解析、`line`/`fork`、`scenario.json` | 2 天 |
| P2 | `dead_end`、`blocker`、`occluder` | 2 天 |
| P3 | 资产接入（Fuel 树/建筑）与植被采样 | 2–3 天 |
| P4 | 批量跑 + 汇总成一张表 | 1–2 天 |

## 10. 风险与对策

- **滑板底座过不了窄门/陡坡**：已知会卡死。窄门宽度先按底盘宽度的 2.2 倍起，逐级收窄。
- **分叉处网格有缝或自交**：生成后做几何校验（面积、法线、非流形边），失败直接报错不落盘。
- **资产拖慢实时率**：Fuel 模型可能很重，必要时换低模或程序化盒体；实时率低于 0.2 就降级。
- **"起点看不见目标"只能生成时校验**：必须在建图阶段做射线检测，事后判断没有意义。
- **跑一次的固定成本**：单次 10–15 分钟，批量必须 headless 后台跑，落盘后统一汇总。

## 11. 需要确认的三点

1. 目标物固定"红房子"，还是要支持红桶、旗子等（影响 `target.type` 与文本查询）。
2. 分叉处用"圆盘叠加"这种近似能否接受（快，但坡度有轻微不连续）。
3. 首轮批量规模：10 个 seed（约 2 小时）还是 20 个（约 4 小时）。
